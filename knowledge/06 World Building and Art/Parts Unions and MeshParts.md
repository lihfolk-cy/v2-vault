# Parts Unions and MeshParts

<!-- tldr:start -->
> [!tldr] TL;DR
> - Avoid: Unions for repeated props -> Model once, import, clone
> - Avoid: Rebuilding a union instead of duplicating it -> Duplicate finished unions
> - Avoid: Setting `RenderFidelity = Precise` everywhere -> `Automatic`

Everything you see in a Roblox world is one of four kinds of geometry: **primitive Parts** (Block, Ball, Cylinder, Wedge, CornerWedge), **solid-model operations** (Unions, Intersects, Negates, all `PartOperation`s), **MeshParts** (imported triangle meshes) and **Terrain** (voxels, see [[Terrain Tools and Terrain API]]). Each has a different cost profile for rendering, physics, memory, place size and iteration speed. Picking the wrong one is the most common reason a map that looked fine in Studio stutters on a phone, or a build that looked "pro" in Blender looks cheap once it is in the game.

This note explains what each kind really is under the hood, when each one wins, the failure modes, and the patterns one production game settled on after building a hub three times and a 49-model enemy roster once.

## The four kinds at a glance

| Kind | What the engine stores | Render cost | Physics cost | Iteration speed | Best for |
|---|---|---|---|---|---|
| Part (Block etc.) | A shape enum + size; geometry generated by the engine | Very cheap, instances well | Cheapest exact collision (box, sphere, cylinder) | Fastest: drag in Studio | Blockouts, floors, walls, colliders, voxel art, stylised "brick" builds |
| Union / PartOperation | A triangle mesh baked from the CSG result, stored as an asset | One mesh per unique union | Fidelity setting, like a mesh | Slow to edit (re-union), fragile | Small numbers of hand-made shapes that need holes or bevels, arches, door cut-outs |
| MeshPart | A reference to an uploaded mesh asset (+ optional texture or SurfaceAppearance) | Cheap per triangle, instances when the mesh and look match | Fidelity setting (Box to PreciseConvexDecomposition) | Needs a DCC tool + upload | Anything organic, detailed, textured, or repeated many times |
| Terrain | 4 x 4 x 4 stud voxels with a material and occupancy | Its own renderer, cheap for large areas | Precise, collides like geometry | Brushes or API | Ground, cliffs, caves, water bodies |

Rule of thumb: **Parts for structure and collision, MeshParts for looks, Terrain for ground, Unions rarely.** The rest of this note is the nuance.

## Primitive Parts

### What they are good at

A Part is the cheapest thing in Roblox. Its collision is an exact analytic shape (a Block collides as a perfect box), it needs no asset upload, and thousands of identical Parts render through instancing. A Part's `Material` gives it a tiling texture for free (see [[Materials MaterialVariants and SurfaceAppearance]]).

Primitive Parts are the right tool for:
- **Blockouts.** Every level should start as grey Blocks. A blockout made of Parts can be measured, walked, playtested and changed in minutes (see [[Level Design for Roblox]]).
- **Colliders.** A visual mesh with `CanCollide = false` plus a handful of invisible Blocks as collision is usually cheaper and more predictable than mesh collision (see [[Collision and Physics Geometry]]).
- **Stylised builds on purpose.** Studs, bricks and voxel art are a legitimate style. One production game built its whole lobby out of 1,231 anchored Parts and WedgeParts for flat cartoon cliffs, because its owner wanted "a normal flat wall" after two rounds of textured meshes looked "patchy".
- **Runtime-generated geometry.** Code can create Parts freely. It cannot create new mesh assets at runtime without `EditableMesh` (see the warning further down).

### What goes wrong

- **Part count explodes.** Voxel and brick builds hit thousands of Parts quickly. Each Part is an Instance with memory, replication and (if not anchored) physics cost. One production game's voxel showcase pieces held 1,000 to 3,000 cells but only 400 to 1,000 Parts after merging runs of same-colour cells. The merge is described in [[Voxel Art - Studs Outlines and Style Kits]].
- **Z-fighting.** Two coplanar faces of different colours flicker. Offset one by 0.01 to 0.05 studs, or remove the hidden face. Roblox's own SLIM docs give 0.01 studs as the separation for coplanar faces.
- **Seams and hairlines.** Parts touching edge to edge can show a one-pixel gap at distance. Overlap them slightly instead of butting them.
- **Surfaces.** Old places still have `Studs` / `Inlet` surfaces on top and bottom faces. Set `TopSurface` and `BottomSurface` to `Smooth` on anything you build by script, or the default stud texture appears on some parts and not others.
- **Size limit.** Parts are capped at 2,048 studs per axis (widely reported; the API page does not state it). Very large floors are built from several Parts or from Terrain.

### Parts as a style versus parts as a blockout

The difference is intention. A blockout made of Parts is temporary and gets replaced 1:1 by meshes later, so it must carry names and pivots that the replacement can map onto. One production game named every greybox piece `Blockout_<Module>` with a `Module` attribute and a bottom-centre pivot, then ran a swap script that replaced 339 cliff and 677 tree blockouts with imported meshes in one pass. See [[Modeling in Blender for Roblox]] for the swap pattern.

## Unions and solid modeling (CSG)

### What a union really is

A `UnionOperation` looks like "a group of parts", but once the operation runs, the engine computes a **new triangle mesh** and stores it as an asset. The original parts are kept inside the union only so you can **Separate** it later. Consequences:

- A union renders as a mesh. Its cost is its triangle count, not the number of parts you combined.
- Every unique union is a unique mesh. **Duplicating** a finished union in Studio makes copies that share the same geometry asset, so they can instance. **Rebuilding** an identical union from scratch makes a new asset that does not.
- Results over **20,000 triangles are simplified down to 20,000** (Roblox docs). Large unions with many curved parts silently lose detail.
- `PartOperation` UVs are always box-mapped (Roblox docs). Materials tile across a union reasonably, but you cannot paint a texture onto a union the way you can onto a mesh.
- A union takes the main part's `Color`, but keeps per-face colours unless `UsePartColor` is on (Roblox docs).
- `SmoothingAngle` smooths shading between adjacent same-coloured faces; 30 to 70 degrees usually looks good, 90 to 180 causes shading artefacts on sharp edges (Roblox docs). It is only editable in Studio.

### When unions are the right answer

- **A hole or bevel in a few pieces.** A doorway cut into a wall, an arch, a round window. Building the same thing in Blender would take longer than one Negate + Union.
- **Arch-shaped trigger or veil geometry.** One production game used arch-shaped unions as the "veil" surfaces inside its zone gates, fitted to each gate's opening, because the shape changed per gate and a union was quicker to fit than a new mesh per gate.
- **One-off landmark shells** that will never be repeated.

### When unions are the wrong answer

- **Anything repeated.** Twenty lamp posts should be one MeshPart duplicated twenty times, not twenty unions.
- **Anything with many curved parts.** Cylinders and balls produce many triangles per curve; a union of ten of them can be heavier than a carefully modelled mesh of the same shape.
- **Anything you will iterate on.** Separating, editing and re-unioning is slow and occasionally fails. A Blender file is the editable source; a union is not.
- **SLIM / streaming LOD.** Roblox's SLIM docs warn that unions and negations "may render missing or distorted" in the generated LOD and suggest moving the operation into its own model. See [[Level of Detail and Model Streaming]].

### Runtime CSG with GeometryService

`GeometryService:UnionAsync`, `SubtractAsync` and `IntersectAsync` replace the older `BasePart:UnionAsync` family. Differences that matter (Roblox docs):
- Inputs do not need to be parented, so you can compute in the background.
- The result is an **array**. With `SplitApart = true` (the default), each disconnected body comes back as its own part.
- Returned parts have no Parent; you parent them. The originals are untouched.
- Results inherit appearance and collision properties from the main part.
- It is asynchronous and costs time. Do not run rapid sequences of CSG calls (destruction systems that subtract every frame are a trap).
- On the client it only works on client-created parts, and nothing replicates from client to server.
- CSG on MeshParts, plus sweep and fragment, require a beta feature in Studio at the time of writing (October 2026).

A safe server-side subtraction that keeps the result's children (attachments, prompts) by swapping geometry in place:

```lua
--!strict
local GeometryService = game:GetService("GeometryService")

-- Cut `cutter` out of `wall` and keep the wall Instance (and its children) alive.
-- Returns true on success. Yields.
local function carve(wall: BasePart, cutter: BasePart): boolean
	local ok, results = pcall(function()
		return GeometryService:SubtractAsync(wall, { cutter }, {
			CollisionFidelity = Enum.CollisionFidelity.Default,
			RenderFidelity = Enum.RenderFidelity.Automatic,
			SplitApart = false, -- one result, so we can substitute it into `wall`
		})
	end)
	if not ok or #results == 0 then
		warn("carve failed:", results)
		return false
	end
	local result = results[1]
	if wall:IsA("PartOperation") and result:IsA("PartOperation") then
		-- Swap geometry, keep children and references to `wall`
		wall:SubstituteGeometry(result)
		result:Destroy()
	elseif wall:IsA("MeshPart") and result:IsA("MeshPart") then
		wall:ApplyMesh(result)
		result:Destroy()
	else
		-- A plain Part cannot take new geometry: replace it
		result.Parent = wall.Parent
		result.Name = wall.Name
		wall:Destroy()
	end
	return true
end
```

The first time `wall` is a plain Block, the function replaces it (a Block cannot hold mesh geometry). After that it is a `PartOperation` and later cuts keep the same Instance.

## MeshParts

### What a MeshPart is

A `MeshPart` points at an uploaded mesh asset (`MeshId` / `MeshContent`), carries an optional `TextureID` or a `SurfaceAppearance` child, and has its own render and collision settings. Things the docs state that people miss:

- **The mesh cannot be swapped by script.** `MeshId` and `MeshContent` are read-only to scripts "as the collision geometry of the mesh cannot be recomputed in real time" (Roblox docs). To change a mesh at runtime, clone a prepared MeshPart, or use `MeshPart:ApplyMesh(source)`, which copies the mesh, texture, collision geometry and the fidelity settings from another MeshPart.
- **`TextureID` can change at runtime.** `SurfaceAppearance` maps cannot (see [[Materials MaterialVariants and SurfaceAppearance]]).
- **20,000 triangles per mesh** is the import limit (Roblox modeling specifications). Split heavier objects into several meshes. One production game's bosses ran 20k to 42k triangles split across about 30 parts, with the largest single part around 6.5k.
- **One material per mesh, one UV set, UVs inside 0..1** (Roblox texture specifications). A Blender object with three material slots becomes three MeshParts on import, or one mesh with one texture if you bake to an atlas.
- **`DoubleSided`** renders back faces, intended for "card" meshes like leaves, hair and cloth (Roblox docs). It costs fill rate; use it only on cards.
- **`RenderFidelity`** chooses the detail level: `Automatic` (Highest under 250 studs, Medium from 250 to 500, Lowest beyond 500, per the docs), `Precise` (always highest) and `Performance` (always low). The docs name "too many MeshParts set to Precise" as a common performance problem. Leave it on `Automatic` unless a silhouette visibly breaks at distance.
- **`CollisionFidelity`** chooses the collision shape (Box, Hull, Default, PreciseConvexDecomposition). It cannot be changed on an already loaded MeshPart from a normal script; create the part with `AssetService:CreateMeshPartAsync` and pass the fidelity in the options, or set it in Studio. Details in [[Collision and Physics Geometry]].

### Why MeshParts are usually cheaper than they look

The renderer cares most about **draw calls** (see [[Art Budgets - Triangles Draw Calls Memory]]). Identical MeshParts instance into one draw call when they share the same mesh content and the same SurfaceAppearance (or the same TextureContent, or the same material when neither exists) (Roblox docs). A forest of 300 copies of four tree meshes is a handful of draw calls. The same forest built from unions or from unique meshes per tree is hundreds.

The practical consequence: **import assets individually and duplicate them in Studio.** The docs warn that importing a whole scene as one file can produce duplicate meshes with different IDs, which blocks instancing. One production game's 87-model zone kit was uploaded as a library of unique meshes once, stored in `ServerStorage`, and every placement was a clone of a template.

### Pivots

A MeshPart's pivot is the centre of the mesh's bounding box unless you change `PivotOffset`. For models, set `PrimaryPart` or `WorldPivot` deliberately:
- **Props:** bottom centre, so `PivotTo(groundCFrame)` puts them on the ground.
- **Gates and doors:** the centre of the opening at floor level, LookVector pointing at the approach side.
- **Wall modules:** the outer bottom corner, so modules snap end to end.

One production game found uploaded meshes arriving with a rotated `PivotOffset` after an FBX upload route; resetting `PivotOffset = CFrame.new()` before measuring or scaling fixed every placement error (see [[Exporting FBX vs GLB]]).

### Vertex colours and palette textures

Two cheap ways to colour a mesh without a full texture:
- **Vertex colours.** The importer keeps them and they multiply with `MeshPart.Color`. Fine for flat-shaded stylised work. The trap: if the mesh has noisy vertex colours and no UVs, you cannot fix it in Studio. One production game's cliff meshes came in with 400 to 900 slightly different orange and tan vertex shades per mesh, which read as "weird patchy lines"; Material and Color changes could not remove them because they multiply. The meshes had to be re-exported with white vertex colours and proper UVs.
- **Palette textures.** A tiny image of colour swatches and UVs collapsed onto the right swatch. Very cheap, and every mesh in a kit shares one texture so they can batch. The trap: a MeshPart with a `TextureID` **ignores `Material` changes** until the TextureID is cleared (measured in one production game), so a later "add real materials" pass had to clear each palette TextureID and set `Color` to the sampled swatch.

### EditableMesh is not a production mesh source

`EditableMesh` and `EditableImage` let code build or deform geometry. They are powerful for tools, but one production game found they **fail in published games by default** (they need specific experience permissions and capabilities), so it never built runtime visuals on them. Treat them as Studio tooling or a deliberate, tested feature, not a default.

## Choosing: a decision table

| Situation | Use | Why |
|---|---|---|
| Greybox of a whole level | Parts | Fast, measurable, replaceable |
| Floor the player walks on | Parts, Terrain or a flat MeshPart with a Box/Part collider | Exact, cheap collision; no snagging |
| Repeated prop (tree, lamp, crate) | MeshPart, cloned | Instancing, low draw calls |
| Hero landmark with unique shape | MeshPart(s), split under 20k tris each | Detail where players look |
| Doorway in a wall, arch, porthole | Union (if few) or modelled mesh (if many) | Union is quicker for 1 to 3 |
| Destruction at runtime | GeometryService (sparingly) or pre-fractured meshes | CSG is async and costly |
| Voxel / LEGO style | Parts merged per colour, or meshes baked per colour | See the voxel note |
| Ground, hills, caves | Terrain | Its own renderer and LOD |
| Invisible collision for a detailed mesh | Parts (Block, Wedge), transparent | Predictable, cheapest |

## Production patterns that held up

These come from one production game that rebuilt its lobby several times and replaced every enemy model.

1. **Visual and collision are separate objects.** Visual meshes `CanCollide = false`, `CanQuery = false`, `CanTouch = false`; a small set of invisible Parts provides collision. A 1,620-ray grid test after a full art swap came back identical because the colliders never moved. See [[Collision and Physics Geometry]].
2. **Decor defaults.** Anchored, `CanTouch = false`, tiny parts `CastShadow = false`, meshes `RenderFidelity = Automatic`. These four settings were applied to every decoration by convention.
3. **Glow and glass are separate meshes.** A kit exported each piece as `Piece`, `Piece_Glow`, `Piece_Accent`, `Piece_Glass`. In Studio the glow mesh became `Neon`, the glass mesh `Glass`, and the accent took a per-station colour. One material per mesh is a limit; it is also a feature.
4. **Merge by colour, not by object.** For voxel and stylised art, the station builds used "one mesh per colour" with a shared stud overlay texture. Ten colours means ten MeshParts per station, regardless of complexity.
5. **Every pass stores how to undo itself.** Moves wrote the old pivot to an attribute (`PreSpread`, `PreFlatGround_Pivot`), recolours wrote the old colour, retexture passes wrote `PreTex_*`. Reverting a pass was a loop over attributes, not a version-history restore. See [[Safe Changes in a Shared Place]].

A tiny helper for that last pattern:

```lua
--!strict
-- Store a reversible "before" value on an instance the first time a pass touches it.
local function remember(inst: Instance, key: string, value: any)
	if inst:GetAttribute(key) == nil then
		inst:SetAttribute(key, value)
	end
end

-- Example: ground every prop in a folder, remembering the original pivot
local function groundAll(folder: Instance, groundY: number)
	for _, m in folder:GetChildren() do
		if m:IsA("Model") then
			local pivot = m:GetPivot()
			remember(m, "PreGround_Pivot", pivot)
			local boxCf, size = m:GetBoundingBox()
			local bottom = boxCf.Position.Y - size.Y / 2
			m:PivotTo(pivot + Vector3.new(0, groundY - bottom, 0))
		end
	end
end

local function revert(folder: Instance, key: string)
	for _, m in folder:GetDescendants() do
		local v = m:GetAttribute(key)
		if typeof(v) == "CFrame" and m:IsA("Model") then
			m:PivotTo(v)
			m:SetAttribute(key, nil)
		end
	end
end
```

## Common mistakes

| Mistake | What it looks like | Fix |
|---|---|---|
| Unions for repeated props | High draw calls, place file grows, every copy re-unioned | Model once, import, clone |
| Rebuilding a union instead of duplicating it | Identical-looking unions that do not batch | Duplicate finished unions |
| Setting `RenderFidelity = Precise` everywhere | Slow frames in busy views | `Automatic` |
| Using mesh collision on walkable floors | Snagging, step-ups, jitter at seams | Box/Part colliders |
| Importing a whole scene as one file | Duplicate meshes with different ids, no instancing | Import each asset once, duplicate in Studio |
| Palette TextureID then trying to change Material | Material changes do nothing | Clear `TextureID` first |
| Butting parts edge to edge | Hairline gaps at distance | Overlap slightly |
| Coplanar faces | Flicker | Offset 0.01+ studs or delete one |
| Trying to set `MeshId` from a script | Error | Clone a template or `ApplyMesh` |

## Checklist

- [ ] Blockout in Parts with names and pivots that the final meshes can map onto.
- [ ] Repeated objects are one mesh asset, cloned.
- [ ] No mesh over 20,000 triangles; heavy objects split.
- [ ] Unions only for a few one-off shapes; none in repeated props.
- [ ] Visual meshes non-colliding; colliders are simple Parts.
- [ ] Decor anchored, CanTouch off, small parts no shadows, RenderFidelity Automatic.
- [ ] Glow, glass and accent pieces are separate meshes.
- [ ] Every bulk pass writes reversible `Pre*` attributes.
